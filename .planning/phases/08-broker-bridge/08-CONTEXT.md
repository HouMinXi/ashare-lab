# Phase 8 Context: Broker Bridge

## 一句话

把 ashare-lab 的每日买卖信号从"纸上谈兵"变成"真金白银"。

## 现在是什么样

```
每天 18:00  pipeline 跑完，生成买卖信号，写入 SQLite
每天 18:00  paper engine 模拟成交（假设全部按收盘价成交）
每天 18:00  微信推送报告（今天买了啥、卖了啥、净值多少）
```

所有这些都是"模拟"——没有真的下过单。

## 要变成什么样

```
每天 18:00  pipeline 跑完，生成买卖信号，写入 orders/{日期}.json
每天 09:10  win-gpu iQuant 策略读取信号，通过 passorder() 真的下单
每天 15:00  iQuant 回写成交结果 fills/{日期}.json
每天 18:00  pipeline 对比模拟成交 vs 真实成交，计算漂移
```

## 架构：双机信号文件桥接

```
X500 (Linux)                         win-gpu (Windows)
  ashare-lab pipeline                  iQuant 客户端（自动登录）
  每日 18:00 生成信号                   Task Scheduler 定时启动
  -> orders/{date}.json                -> iQuant 策略读取 JSON
  -> rsync/scp 同步到 win-gpu          -> passorder() 逐笔下单
                                       -> fills/{date}.json
  <- rsync/scp 回写成交结果 <-----------
```

## 为什么选国信 iQuant

2026年7月量化环境剧变：miniQMT 全行业关闭（7/6），华鑫个人 CTPAPI 直连已堵。

| 对比项 | 国信 iQuant | 国金 QMT | 华鑫 QMT |
|--------|------------|---------|---------|
| 自动登录 | 支持 | 不支持 | 待确认 |
| 已有账户 | 是 | 是 | 仅模拟盘 |
| 佣金 | 万1可谈 | 万1 | 待确认 |
| 策略文件 | 明文GBK | 默认加密 | - |

自动登录是决定性优势——无人值守日频策略必须能定时自动启动。

## P0-3: 第一天怎么起步

paper engine 手里有一整个模拟持仓（15 只股票），真实账户开出来是 100% 现金。

问题：pipeline 生成的是增量信号（今天买谁卖谁），对着空账户执行增量：
- 卖单卖的是真实账户根本没有的股票 → 被拒
- 买单因跳空跳过而买不全
- 两本账从第一天起就发散，对账模块只会看着它发散

**必须决定的方案**（二选一，在 ADR-0003 中白纸黑字）：

**方案 A：整体建仓**
- 第一天不做增量信号，而是把 paper engine 的目标持仓整体下单
- 优点：两本账从第一天起就对齐
- 缺点：一次性下单 15 只，需要足够的现金

**方案 B：从零开始，只比收益率**
- 真实账户从零开始，只跟踪增量信号
- 不比持仓，只比累计收益率
- 卖单必须先查真实持仓再截幅（没有的股票不卖）
- 优点：简单，不需要特殊处理
- 缺点：前 30 天两本账持仓完全不同，对账无意义

**建议选方案 A**，因为对账是 Phase 8 的核心验证目标。

## 关键架构变更

**原计划 (ADR-0001)**：X500 生成订单 -> Windows GPU Box 上的 QMT 下单

## 最大的风险（必须在实盘前解决）

### 1. 符号格式不一样

qlib 用 `SH600000`，iQuant 用 `600000.SH` 或纯 `600000` + 交易所字段。
**解决**：写 `qlib_to_iquant()` 转换函数，bridge 启动时校验所有符号。

### 2. 科创板最小手是 200 股

paper engine 硬编码了 100 股一手。科创板 (688xxx) 最小买入是 200 股。
**解决**：`get_lot_size(symbol)` 函数，科创板返回 200。

### 3. iQuant 必须在 Windows 上运行

不像 CTPAPI 可以在 Linux 跑，iQuant 必须在 win-gpu 上。
**解决**：信号文件桥接——X500 生成 JSON，rsync 到 win-gpu，iQuant 策略读取执行。

### 4. 隔夜缺口

paper 假设 0.1% 滑点。实盘开盘可能跳空 5%+。
**解决**：限价单 + 开盘偏差超 2% 就跳过。

### 5. win-gpu 宕机或 iQuant 未启动

如果 win-gpu 在 09:10 没启动或 iQuant 没登录，订单不会提交。
**解决**：Task Scheduler 自动启动 + 登录状态检查 + 微信告警。

### 6. 信号文件同步失败

X500 到 win-gpu 的 rsync 可能因网络问题失败。
**解决**：重试机制 + 校验文件完整性（SHA256）+ 微信告警。

## 数据量不是问题

| 指标 | 我们 | 券商限制 | 余量 |
|------|------|---------|------|
| 每日订单 | 2-15 | 6单/秒 | 差 3-4 个数量级 |
| 峰值订单 | ~30 | 6单/秒 | 5 秒搞定 |

真正的挑战不是"能不能下单"，而是"下单格式对不对"。

## 模拟环境

iQuant 内置模拟盘功能，开通 iQuant 权限后即可使用，不需要额外的模拟服务器地址。

## 数据管道风险

| 数据 | 风险 | 说明 |
|------|------|------|
| 收盘价 | 中 | 17:00 tushare 拿到的可能是初值，21:00 才有修正值，但 pipeline 18:00 就用了 |
| ST 标记 | 中 | 缓存 + 正则匹配，best-effort |
| 基准指数 | 中 | 如果缓存没命中 + 网络失败，静默降级到 0.0，没有告警 |
| baostock | 低 | 全部有缓存优先 + 超时降级 |
| 停牌/涨跌停 | 低 | paper engine 已正确处理 |

## 备用方案

**如果国信 iQuant 出问题**：国金证券 QMT 已开户（8890836643，万1），API 互通（passorder 一样），代码迁移成本为零。缺点是无自动登录。
**如果 CSRC 报备延迟**：先报备后交易，必须在实盘前完成。
**如果 bridge 挂了当天没下单**：信号排队到下一个交易日，或者手动下单。

## 舰队面注意

P1-4: X500 上真金白银的 bridge 和 harness dispatcher 同住一台机器。交易时段 X500 全员冻结变更（J2 契约）。

## 关键代码插入点

1. **订单生成**：pipeline step 10 后，把 pending orders 导出为 JSON
2. **文件同步**：rsync orders JSON 到 win-gpu
3. **iQuant 策略**：win-gpu 上 iQuant 策略脚本读取 JSON → passorder()
4. **成交回写**：iQuant 策略写入 fills JSON → rsync 回 X500
5. **成交导入**：pipeline step 8 前，读取 fills JSON，更新订单状态
6. **对账**：对比 paper engine 的模拟成交 vs bridge 的真实成交
7. **独立数据库**：bridge 用 `broker.db`，不污染 `paper.db`

## 2026-07-21 架构更新：TORA -> QMT Bridge

**决策**: 券商从华鑫证券 openctp-ctp TORA 改为国金证券 QMT + QMT Bridge。

**原因**:
1. QMT Bridge 是开源 HTTP/WebSocket 封装（syfly007/qmt-bridge），X500 直接 HTTP 调用 win-gpu
2. 国金 QMT 佣金万1可谈，无每笔最低（iQuant 每笔最低5元）
3. miniQMT 支持个人下单（iQuant miniQMT 不支持）
4. 同一 passorder() API，iQuant 可作备选（配置迁移）

**架构变化**:
- 旧: X500 -> rsync 信号文件 -> win-gpu iQuant -> passorder()
- 新: X500 -> HTTP POST -> win-gpu QMT Bridge -> passorder()

**备选**: 国信 iQuant + 信号文件桥接（如 QMT 自动登录不可靠）
