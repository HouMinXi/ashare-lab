# 08-01-PLAN: 国金 QMT + QMT Bridge Broker Bridge

## Objective

Build a broker bridge module that submits ashare-lab's daily buy/sell signals to 国金证券 via QMT Bridge (HTTP API), replacing the paper-only execution path with real order submission capability.

## Architecture

**Key decision**: X500 (Linux) calls QMT Bridge HTTP API on win-gpu (Windows). QMT runs on win-gpu with pyautogui auto-login.

```
Pipeline (18:00, X500) -> orders/{date}.json -> HTTP POST to win-gpu:8080 -> QMT Bridge -> passorder() -> fills
```

X500 generates signals at 18:00, queues orders as JSON files. At 09:10 next day, the bridge reads the order file, calls QMT Bridge HTTP API on win-gpu to submit orders, receives fill callbacks via WebSocket. Paper engine continues running in parallel for reconciliation.

**Architecture changes from ADR-0001**:
- Broker: 国金证券 QMT (account 8890836643, 万1 可谈, no per-order minimum)
- Bridge: QMT Bridge (open-source HTTP/WebSocket wrapper around xtquant, syfly007/qmt-bridge)
- X500 calls win-gpu HTTP API directly (no signal file bridging needed)
- Auto-login: pyautogui script on win-gpu (community-maintained, 2026 edition)
- Separate `broker.db` (not extending `paper.db`)

## Day-1 Bootstrap Strategy

Paper engine holds a simulated portfolio (15 stocks). Real account starts at 100% cash. The pipeline generates incremental signals (buy/sell today) — executing incremental against an empty account fails:

- Sell orders for stocks the real account doesn't have → rejected
- Buy orders skipped due to gap → buy incomplete
- Two books diverge from day 1

**Decision required (in ADR-0003):**

**Option A: Full portfolio build (recommended)**
- Day 1: submit the entire paper target portfolio as buy orders
- Pros: two books aligned from day 1, reconciliation meaningful
- Cons: needs enough cash for 15 simultaneous buys

**Option B: Start from zero, track returns only**
- Real account follows incremental signals only
- Don't compare positions, only compare cumulative returns
- Sell orders must query real holdings first, skip if not held
- Pros: simple
- Cons: first 30 days positions completely different, reconciliation meaningless

**Recommend: Option A** — reconciliation is Phase 8's core validation goal.

**Unconditional sell-side clamp (P0-3)**: regardless of Option A or B, the bridge MUST query real holdings before submitting any sell order. Sell qty is capped at `min(target_qty, real_holdings)`. Under Option A, gap_skip and partial fills also create paper-vs-real position gaps; first sell of an under-held stock gets rejected by the exchange (A-share short selling prohibited). The clamp prevents this.

**Drift repair policy (P0-3)**: if position mismatch persists >N consecutive trading days (suggest N=5), the pipeline generates corrective orders to close the gap, or raises an iLink alert for manual fix. Without repair, drift accumulates silently and reconciliation becomes meaningless after the first gap_skip event.

## Design Decisions

### D1: File-based decoupling with atomic writes

Orders are exchanged via JSON files, not direct function calls. Atomic write pattern: write to `.tmp`, `fsync()`, `rename()`. Sentinel `.complete` file signals readiness. Pipeline checks sentinel before reading.

### D2: QMT Bridge architecture

Use QMT Bridge (HTTP/WebSocket wrapper around xtquant) instead of direct broker API. Reasons:
1. QMT Bridge eliminates signal file bridging — X500 calls HTTP API directly
2. 国金 QMT has no per-order minimum (iQuant has 5 CNY/order)
3. miniQMT supports individual trading (iQuant miniQMT does not)
4. Same `passorder()` API as iQuant — config-only migration if needed
5. QMT Bridge is open-source (100+ endpoints, WebSocket, API key auth)

### D3: Limit orders at close price with gap guard

Submit limit orders at the previous day's close price. If the stock gaps >2% at open, skip the order (`gap_skip`). If unfilled by 14:00, cancel (`timeout_cancel`).

**Gap guard data source (F5)**: Bridge needs current-day open price at 09:15. QMT Bridge provides market data API (`GET /api/quote/realtime`) for the 15 symbols in today's order file. Compare open vs previous close. Skip if deviation > threshold.

**Market data failure policy**: If QMT Bridge market data API fails or returns stale data, the bridge must NOT silently skip gap checking. Policy: (1) Wait for first tick; then start 30s timer. If no tick arrives by 09:30:30 (continuous trading start + 30s), declare `gap_guard_failed` and skip ALL orders. (2) If market data drops mid-session, continue with last-known prices and log WARNING. iLink alert on market data failure.

### D4: Parallel paper execution

Paper engine continues running `settle_day()` for tracking. The reconciliation table compares paper vs real fills daily.

### D5: Separate broker.db

Bridge gets its own `broker.db` with `submissions`, `fills`, `sessions` tables. No shared SQLite access with paper.db. File-based exchange eliminates all contention.

### D6: QMT Bridge HTTP/WebSocket architecture

QMT Bridge exposes HTTP REST API + WebSocket for real-time updates. Bridge calls `POST /api/trading/order` to submit orders, receives fill updates via WebSocket. No callback threading needed — QMT Bridge handles all xtquant threading internally.

### D7: Single long-running bridge process

QMT Bridge maintains persistent WebSocket connection. Single process with crash recovery: on restart, query QMT Bridge for existing orders, dedup by `order_ref`, submit remaining.

**Crash recovery dedup (F19)**: On restart, query QMT Bridge for ALL orders submitted today (not just pending). For each order_ref found: if status is filled/partial, adopt the fill; if status is pending/live, do NOT resubmit — wait for it to fill or expire. Only submit orders with no matching order_ref.

### D8: systemd simple + timer at 09:10

Bridge runs as systemd service (Type=simple) triggered by timer at 09:10 CST. Use explicit timezone: `OnCalendar=*-*-* 09:10:00 Asia/Shanghai`. Pre-flight probe: verify QMT Bridge HTTP API is reachable on win-gpu before submitting orders. Restart=on-failure, StartLimitBurst=3.

**Bridge lifecycle**: process starts at 09:10, checks QMT Bridge health, submits orders from 09:15 (after gap guard), monitors fills until 15:00. Exit code: 0 on clean EOD, non-zero on fatal error. At 15:00: write `fills/{date}.json` (atomic: `.tmp` + `fsync()` + `rename()` + `.complete` sentinel), cancel any remaining unfilled orders, exit cleanly (code 0). If any orders still partial at 15:00, cancel remaining qty and record final aggregated status as `partial_cancelled` in fills file. If bridge crashes at 14:59: next-day bridge startup queries QMT Bridge for ALL orders since `last_eod_date` (tracked in broker.db sessions table). Retroactively writes missing fills files, then proceeds with today's orders.

### D9: Multi-dimensional kill switch

Beyond 10% NAV drawdown:
- Single-stock 15% loss
- 5-day 3% drawdown
- Fill rate <70%
- Alpha IC <0 for 4 consecutive weeks

### D10: Stop-on-error policy

Fatal errors (auth failure, batch-wide symbol mapping failure) halt entire batch. Per-order symbol mapping failure: skip that order, log ERROR, continue (aligned with 08-01-B validation rules, R3-LC6). Connection drops: retry up to 3 times with 10s backoff; if all retries fail, halt remaining unsubmitted orders and log fatal. Per-order rejections (insufficient funds, price limit) log and continue (R2-F5: graduated connection drop policy, not immediate halt).

## Order File Format

**Note**: `order_id` in JSON = `paper.orders.id` in SQLite = `paper_order_id` in broker.db submissions table. All three are the same integer value, used as the join key between paper engine and broker bridge (P1-F1, INT-F1).

**broker_order_ref (R1-F10, R3-LC4)**: Bridge sets QMT `order_ref = str(paper.orders.id)` at submission time, making `broker_order_ref == order_id` by construction. QMT enforces order_ref length limit. Guard: `assert len(ref) <= 21` at submit site; use fixed-width format `f"{id:012d}"` if auto-increment IDs ever approach 10^12. This is the join key between fill file and order file — no separate mapping table needed.

1. **Unit tests**: QmtBridge methods with mocked HTTP API (target 90%+ line coverage)
2. **dry-run tests**: `--dry-run` flag, no network needed, CI test mode
3. **Integration tests**: QMT simulation with real HTTP API calls
4. **Simulation validation**: QMT simulation environment during market hours
5. **Reconciliation tests**: Inject known drift, verify alert triggers
6. **Kill switch tests**: Inject NAV drawdown, verify order halt
7. **Crash recovery tests**: Kill bridge mid-batch, restart, verify dedup. **Retroactive fills test**: (1) submit 5 orders, (2) crash at 14:59, (3) simulate T+1 startup, (4) verify retroactive fills file written, (5) verify `qmtbridge --backfill` re-imports correctly.

9. **Lot size tests**: STAR 200-share, main board 100-share, odd-lot sells
